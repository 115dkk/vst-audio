## Executive summary

- 95 findings: High 10, Medium 46, Low 39. No Critical after re-ranking: every memory-safety
  defect found is inside the worker, whose crash the isolation contract already contains.
- **Isolation boundary (TD-01, TD-02, TD-03).** On Linux without `memfd_create` the shared
  mapping silently falls back to an unsealed file the worker can truncate, which turns a plugin
  bug into an application `SIGBUS`. On Windows the IPC and mapping handles stay inheritable in the
  application, so an unrelated `CreateProcess` (Rust's `std::process::Command` included) copies
  them. In the worker, the original inherited descriptors are never closed or made
  non-inheritable, so a plugin's helper process inherits the control pipe and the mapping.
- **Realtime and supervision (TD-04, TD-05).** The worker's `drain` processes blocks until the
  ring is empty and only then beats the heartbeat, so a producer that keeps the ring fed (offline
  rendering) gets a healthy worker killed after 500 ms. A runtime `LatencyChanged` updates the
  event stream but not the endpoint's reported latency or its fallback delay line.
- **Foreign ABI validation (TD-06, TD-07, TD-08, TD-09).** A VST2 MIDI event is referenced as a
  full record before its declared size is checked. VST3 bus negotiation does not re-check bus
  counts after read-back. A VST3 state restore can be overwritten by a parameter queued before it.
  The VST2 callback validates parameter IDs against the pre-OPEN count.
- **Release process (TD-10).** When the bump push is rejected the gate rebases onto the new
  `main` and releases it with the bump it computed before, so a `feat!` that lands meanwhile can
  ship as a patch.
- **Supervisor and error shape (TD-11 to TD-17).** Requests that end in a worker Fault or a Watch
  disable never get their `RequestFailed`. `StartError(String)` carries every failure kind, so a
  caller cannot tell a full queue from a dead worker. `supervise()` is a 650-line function with
  three copies of the recovery hand-over.
- **Tests that do not test what they claim (TD-20 to TD-24).** The ring no-alloc test never
  reaches a delivered block, the ring fuzzer never feeds a corrupted output packet, the control
  fuzzer's Hello seed is a protocol major behind, and worker-side processing has no allocation
  guard at all.
- **Documentation drift (TD-71 onward).** Architecture still describes the old libX11
  `RTLD_NOLOAD` lookup, support.md contradicts itself on VST2 gesture forwarding, two crate docs
  cite an ADR 0021 that this repository does not have, and the worker distribution summary
  hardcodes "20 passed".

## Architectural mental model

The application links `vst-audio`, which owns a `Host` (worker selection and launch), one
`Instance` per plugin (a supervisor thread plus a bounded request/event pair) and one realtime
endpoint (`AudioEndpoint` or `BlockEndpoint`) that only touches pre-allocated buffers and the
shared ring. `vst-audio-protocol` is the bounded control codec and the deterministic Watch state
machine; `vst-audio-ring` is the shared-memory block ring and its `BlockLane` client. Both are
pure and run on both sides. `vst-audio-transport-sys` owns OS processes, pipes, wakeup events and
mappings, and is where inheritance and teardown are decided. The worker executable calls
`vst-audio-worker-runtime::host::main`, whose `native::host_main` loop runs requests and the
native editor on the main thread and hands the only processor to an audio thread;
`vst-audio-worker-sys` holds the VST2/VST3 ABI, module loading and native editor windows.

This matches the README and `docs/architecture.md`, with one exception: the public
`worker-runtime::host::Session` state machine (`crates/vst-audio-worker-runtime/src/host.rs:47`)
reads like the worker's lifecycle, but the executable never uses it. The real policy lives in
`native::host_main`, and the two already disagree (TD-29).

## Top 5 "if you fix nothing else, fix these"

1. **TD-04: beat inside drain.** In `AudioBuffer::drain` (`crates/vst-audio-worker-runtime/src/host.rs:184`) call `consumer.beat()` after `consumer.complete(0, sequence)`. One atomic store per block keeps the heartbeat alive under a fed ring; a regression test publishes blocks continuously for 1 s through a test consumer and expects no `Disable`.
2. **TD-01 and TD-03: keep the mapping sealed and the originals private.** Remove the `ENOSYS` fallback in `backing_file` (return the error), and check `fcntl(F_GET_SEALS) & (F_SEAL_SHRINK | F_SEAL_GROW)` in `SharedRegion::open` on Linux. In the worker bootstrap, after `duplicate_value`, close each inherited original (Unix `close`, Windows `CloseHandle`) unless a later step still needs that number.
3. **TD-06, TD-07, TD-09: validate before trusting the plugin.** In `vst2_events.rs` read `size` first and require `declared >= size_of::<MidiEvent>()`, then read `offset` and `data` through `ptr::read_unaligned` of the fields. In `vst3.rs` compare `actual.len() == requested.len()` for both directions before the `zip`. In `plugin.rs` store the post-OPEN `num_params` into `callback.parameter_count`.
4. **TD-05 and TD-13: latency follows the worker.** Add `latency: AtomicU32` to `Shared`, store it with each `LatencyChanged` and recovery, and let the endpoint read it at its next block boundary into `active.latency` (bounded by `latency_bound_frames`); keep the new control's latency in `restore_watch`.
5. **TD-10: decide the bump on the head you push.** In `_commit_bump`, when the push is rejected, stop instead of rebasing: raise a distinct exit so the next workflow run (which the new `main` push starts) decides from the new head.
